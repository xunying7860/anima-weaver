## 0. 先说结论

你说的「节点过多、冗长」，**根因不是节点真的多，而是主节点不自声明输入，靠另外两个节点把控件序列化成 JSON 再喂回来**。

我扫了 `AnimaWeaver.INPUT_TYPES` 声明的键，和代码里 `kwargs.get(...)` 实际读的键，对不上：

```
INPUT_TYPES 声明: 33 个键
代码里读取但未声明: 8 个键
   排除含标签列表 / 排除标签分类 / 标签列表必含 / 过滤标签
   自然语言描述 / 详细 NL 系统提示词 / aspect_ratio / _preloaded
```

再加上 8 个槽位（`人数/身份` `外貌` `服装` `姿势/动作` `表情` `镜头` `场景/环境` `细节/氛围`）—— 它们是通过 `slot_keys` 列表用变量读的，同样**没有声明在 INPUT_TYPES 里**。

也就是说：

- **`AnimaWeaver` 单独拖出来是残废的**。`manual` 模式下 8 个槽位全是空；`_run_raffle` 里的 `通用标签/争议标签/敏感标签/露骨标签` 4 个开关也全是 `False`，只能走兜底 `["taglists-sensitive.txt", "taglists-explicit.txt"]`。
- **`提示词槽位` 和 `底部控制` 不是「可选增强」，是「必需配件」** —— 它们存在的唯一理由是主节点塞不下这些控件，只好做成独立节点再 `json.dumps` 成一个 STRING 传回去。

所以整合的方向很明确：**不是删节点，是让主节点自己声明这些输入**，JSON 中转这一层直接消灭。

### 1.1b 控件太多 → 做成二级菜单（分组折叠）

**结论：能做，但 ComfyUI 没有原生语法，要写前端扩展。**

`INPUT_TYPES` 只有 `required` / `optional` / `hidden` 三层 —— **没有 group / section / tab 这类分组语法**，也没有官方的「二级菜单」。所以要么自己做，要么用现成方案。

#### 三种做法对比

| 方案 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| **A. 分组折叠开关**（推荐） | Python 声明 N 个 BOOLEAN 组开关，JS 监听开关值 hide/show 该组控件 | 原生 widget，序列化零风险；可同时展开多组；展开状态随工作流保存；后端不用改 | 要写 ~150 行 JS |
| **B. 单个分组 COMBO** | 一个下拉「参数分组: 常用/槽位/过滤/LLM/批量」，单选显示 | 最简单，几十行 | 一次只能看一组，切换来回麻烦 |
| **C. Subgraph 子图** | 把槽位节点打包成子图，双击才展开（前端 1.24.3+ 原生） | 零代码，原生功能 | 得用户手动创建，**不能作为插件默认形态**；且子图是另一个节点，不是"主节点里的二级菜单" |

**推荐 A**，已写好可直接用的实现：`js/anima_groups.js` + `patches/04_input_types_grouped.py`。

#### 长什么样

```
AnimaWeaver
├─ 模式          [hybrid ▾]        ← 一级，常驻
├─ 标签比例      0.6
├─ 场景类型      [solo_display ▾]
├─ 随机种子      ──○──
├─ ☐ ▸ 标签槽位                    ← 二级入口，默认收起
├─ ☐ ▸ 过滤控制
├─ ☐ ▸ LLM设置
├─ ☐ ▸ 批量
└─ ☐ ▸ 高级
```
勾选「▸ 标签槽位」后，下面原地展开 9 个槽位控件；取消勾选就收起，节点高度实时收缩。

#### 实测效果（本机端到端仿真，mock 21 个 widget）

```

展开「标签槽位」：隐藏剩 8 个，高度 398 px
再次收起：完整还原，widgets 数组长度始终 21 不变
```

#### 三个必须知道的坑（实现里都处理了）

**1. 隐藏 widget 不能从 `node.widgets` 数组里移除。**
移除会改变索引，而前端保存 `widgets_values` 是 index-based 的 —— 会直接错位，**污染所有打开的工作流并被自动存回磁盘**。所以只改显示属性，不动数组。

**2. 隐藏要设三件套，只改 `widget.type` 不够。**
```js
w.hidden = true;
w.options = w.options || {}; w.options.hidden = true;
w.computeSize = () => [0, -4];
for (const k of ["element", "inputEl"]) { const el = w[k]; if (el?.style) el.style.display = "none"; }
```
STRING 类 widget 会创建真实 DOM `<input>` 并按 canvas 坐标定位，**不设 `display:none` 的话它照样画出来**。

**3. 组开关必须是原生 BOOLEAN，不能用 `addDOMWidget`。**
DOM widget 必须 `serialize = false` 且**只能 append 到 `node.widgets` 末尾**（前端 save 是 index-based、restore 是 compacting counter，两者不对称，插中间必错位）。这就意味着它没法放在分组前面 —— 所以组开关只能用原生 widget。

#### 要改的地方

```python
# __init__.py  —— 现在没有这行，必须加
WEB_DIRECTORY = "./js"
__all__ = ["NODE_CLASS_MAPPINGS", "NODE_DISPLAY_NAME_MAPPINGS", "WEB_DIRECTORY"]
```

```python
# anima_weaver.py —— INPUT_TYPES 换成 04 号补丁里的 build_input_types(model_list)
# 顺序约束：组开关（"▸ xxx"）必须排在它管理的 widget 前面
#           默认约束：槽位 widget 默认值一律 ""，否则会盖掉「提示词槽位」节点传来的值
```

**默认值这条最关键**：`compose()` 的合并逻辑是「widget 为空时才用 JSON 注入的值」。一旦给槽位设了非空默认值，旧工作流接的 `提示词槽位` 节点就失效了。过滤组里 `敏感标签/露骨标签` 是**真实开关**（不是组开关），默认值必须保持 `True`，否则开箱行为和现在不一致。

#### 顺带：原生 Collapse 也能用

节点左上角灰点 / 右键 `Collapse` 可以把整个节点收成只剩标题条。适合已经调好参数、只想省地方的场景 —— 但那是「整个节点折叠」，不是分组，和上面的方案可以叠加使用。

## 2. 性能：三处 IO 灾难（这才是「冗长」的体感来源）

### 2.1 `_run_raffle()` 每个种子全量重扫 —— 最严重

`anima_weaver.py:601` 的 `_run_raffle` 每次调用都：
1. 重新解析 `categorized_tags.txt`（59575 条）→ **34~68 ms**
2. 打开 taglist 逐行扫到 5000 行才 `break`（文件 47~59 MB）→ **55 ms**

而 `_compose_batch()` 在 `for i, seed_str in enumerate(seeds)` 循环里**对每个种子调一次**：

| 批量 N | 现状纯 IO/解析耗时 |
|---|---|
| 16 | 1.3 s |
| 64 | 5.2 s |
| 256 | **21.0 s**（还不含 LLM 推理） |

**隐藏 bug**：`if len(valid_taglists) >= 5000: break` —— 文件有 **100000 行**，所以**只有前 5% 的标签组合永远抽得到**，后面 95% 白占 216 MB 磁盘。

**改法**（补丁 `01_tag_index.py`）：建一次行偏移表（落盘 `.idx` 缓存），之后一次 `seek + readline`；分类字典模块级缓存；过滤改成「随机探测」而非全量扫描。

实测：

```
建表(全文件扫描): 0.03 s, 100000 行
二次加载(磁盘缓存): 0.027 s
分类字典首次 186 ms -> 缓存后 0.0046 ms
pick_taglist 单次 0.47 ms  vs  原 _run_raffle 49.5 ms   → 加速 105 倍

批量 N=16 : 0.8 s  -> 0.008 s
批量 N=64 : 3.2 s  -> 0.030 s
批量 N=256: 12.7 s -> 0.120 s
```

顺带：探测式抽签解锁全部 10 万行，标签多样性直接 ×20。

### 2.2 画师查询 O(n) 全文件扫描

`artist_seed.py::_get_artist_name(idx)` **每查一个画师扫一遍 804 KB 文件**，实测 3.7~23 ms/次。批量 100 个种子 ≈ 0.37 s 纯浪费。
而且画师索引有 **3 套独立实现**（`anima_weaver._load_artists` / `artist_seed._get_artist_count` / `_get_artist_name`），内存里存了两份 59k 列表。

**改法**（补丁 `02_artist_index.py`）：统一成一个模块级单例，加载一次，O(1) 序号查名。
实测：**3.7 ms → 0.00022 ms（快 16304 倍）**，批量 100 种子 `0.37 s → 0.0000 s`。

### 2.3 `INPUT_TYPES()` 里同步跑 `lms` 子进程

`anima_weaver.py:79` 调 `get_models()` → `_run_lms(["ls"])` → `subprocess.run(timeout=60)`。

ComfyUI **每次刷新页面 / 打开节点菜单都会请求 `/object_info`**，也就是每次都 fork 一个 `lms` 子进程。LM Studio 没装时 `shutil.which` 失败很快；装了但服务没响应就是 **60 秒阻塞**。

**改法**（补丁 `03_lm_studio_fix.py`）：缓存 5 分钟 + 后台线程刷新 + 未命中先返回 `(检测中…)`，永不阻塞。同时把 `ls` 这类轻量查询的 timeout 从 60 s 降到 5 s。

## 2b. 随机逻辑：7 处问题 + laya-0.4b 的落地点

> **先说一个实测结果，它否掉了一个看起来很自然的用法**：
> `categorized_tags.txt` 对实际抽到的 tag 覆盖率是 **99.4%**（10960 个 tag 中只有 69 个查不到，0.6%）。
> 所以**别把 laya 用在「槽位分类补全」上** —— 只有 0.6% 的收益空间，不值得。

### 2b.1 先修不需要 laya 的那 5 处（纯规则 bug，实测确认）

| # | 位置 | 问题 | 实测 |
|---|---|---|---|
| 1 | `anima_weaver.py:674` | `rng.shuffle(enabled_files)` **纯浪费** —— shuffle 改变了列表顺序，但下一行 `enabled_files[seed % len]` 的下标只取决于 `seed`，shuffle 消耗了 rng 状态却不影响结果 | seed=1→`a`，shuffle 后仍是取 index 1 |
| 2 | `anima_weaver.py:675` | `seed % len(enabled_files)` → **奇偶决定**，完全可预测，毫无随机性 | seed 1~10 严格交替两个文件 |
| 3 | `anima_weaver.py:716` | `seed % len(valid_taglists)` → 过滤条件越严候选池越小，**多样性崩塌** | 候选池 5 行 → seed 1..20 只有 5 种结果（多样性 25%）；2 行 → 10% |
| 4 | `anima_weaver.py:587` | `raffle_tags[:8]` 机械截断，撞上槽位分布极不均 | 见下表 |
| 5 | `anima_weaver.py:410`<br>`artist_seed.py:89` | 画师用 `random.randint`（非 `rng`）→ **不受 seed 控制，种子不可复现** | 同一个 seed 重跑，画师会变 |
| 5b | `_run_raffle` 输出 | **5.3% 的 tag 是 Danbooru 元数据**，直接进了提示词 | 见下 |
| 5c | 抽签结果 | 每行标签数失控，中位数 45、**最大 746** | 见下 |

**5b 展开 —— 垃圾标签实测**（抽样 5000 行 / 241424 个 tag）：

```
垃圾标签 12812 个 (5.3%)
  highres 4609 | absurdres 2281 | commentary 2245 | commentary_request 990
  english_commentary 853 | artist_name 404 | bad_id 247 | signature 209
  twitter_username 188 | english_text 171
```

这些是 Danbooru 的**元数据，不是画面内容**。把 `commentary`、`absurdres`、`bad_id` 塞进提示词，等于告诉 SD「请生成一张有评论的、分辨率爆表的、ID 损坏的图」—— 要么无响应，要么产生不可预测的副作用。补丁 `05_random_logic.py` 里有一份 `META_TAGS` 黑名单 + `QUALITY_TAGS`（可选，有人刻意在提示词里放 `masterpiece`）。

**5c 展开 —— 标签数失控**：`min=18 / 中位=45 / p95=75 / max=746`，超过 100 个 tag 的行占 0.9%。CLIP 的 77 token 大约只吃前 20 个 tag，后面全是白给。

顺带一个发现：`assembly.SLOT_LIMITS` 设计好的上限**从来没被应用过** —— `assemble_prompt()` 是死代码（pyflakes 报 `anima_weaver.py:26: assembly.assemble_prompt imported but unused`）。这个 cap 逻辑本来就是为了解决 5c 的。

**第 4 条展开 —— 槽位失衡是随机质量差的真凶**（实测 300 个候选）：

| 槽位 | 平均抽到 | cap 8 后 | 利用率 | 最终占比 |
|---|---|---|---|---|
| clothing | 16.0 | 8 | **48.7%** | 24.3% |
| appearance | 14.6 | 8 | **53.8%** | 24.5% |

### 2b.1b 更深层：随机内核本身就是设计问题

上面 7 处不是 7 个独立 bug，是**同一个根因的 7 种表现**：

> **「随机数发生器」和「随机数的用法」被混在了一起。**
> 取模不是随机，位置截断不是抽样，一个 rng 干所有事必然耦合。

现状链路：
```
rng = random.Random(seed)
rng.shuffle(enabled_files)                      # ① 消耗状态但结果被丢弃
selected_file = enabled_files[seed % len(...)]  # ② 取模，不用 rng
...扫 5000 行...
selected_tags = valid_taglists[seed % len(...)] # ③ 取模，不用 rng
...分槽...
combined = list(raffle_tags[:8])                # ④ 位置截断
```

**① `rng.shuffle` 是纯浪费** —— shuffle 改了列表顺序，但下一行用的是 `seed % len` 的下标，只取决于 seed。白消耗 rng 状态。

**② 种子奇偶 = 文件选择，0 bit 随机性** —— seed 1..12 严格交替 `explicit, sensitive, explicit, sensitive...`。`seed % 2` 只用掉 **1 bit，丢弃 63 bit**。

**③ 熵塌缩**：

| 用法 | 有效熵 | 丢弃 |
|---|---|---|
| `seed % 100000` | 16.6 bit | 47.4 bit |
| `seed % 5000` | **12.3 bit** | 51.7 bit |
| `seed % 2` | **1.0 bit** | 63.0 bit |

而且顺序种子（用户手填 1,2,3… 或外部递增）会命中**相邻行**：seed=1→row 1，seed=2→row 2，seed=3→row 3。

**④ `[:8]` 不是「截断」，是系统性字母序偏差** —— 这条最有杀伤力：

实测 **400/400 行的标签是完全按字母序排列的**（Danbooru 导出特性）。所以 `raffle_tags[:8]` 永远取「字母序最靠前的 8 个」：

| 首字母 | 全量分布 | `[:8]` 截断 | 随机抽样 |
|---|---|---|---|
| b | 15.7% | **23.2%**（+48%） | 14.2% |
| a | 4.5% | 6.8% | 4.6% |
| s | 14.3% | **9.9%**（−31%） | 14.7% |
| t | 5.8% | **1.8%**（−69%） | 5.0% |
| w | 3.4% | **1.8%**（−47%） | 3.6% |

随机抽样几乎完美复现全量分布，`[:8]` 严重偏离。**clothing / appearance 被截断时，永远优先保留 a/b/c 开头的标签，t/s/w 开头的几乎进不来。**

**⑤ 一个 rng 干所有事 = 耦合**：

```
seed=100，只改标签数量：
  tag数=10 -> 画师 43177
  tag数=40 -> 画师 25406
  tag数=80 -> 画师 47660
```
改任何一个环节都会连锁改变所有下游结果。「固定种子复现」实际是失效的。

#### 重构：四件事

补丁 `patches/06_random_core.py` 实现了前三件（零风险，行为可对照）：

**1. 命名子流（解耦）** —— `blake2b(seed, name)` 派生独立 `Random`。实测：seed=100，tag 数 10/40/80 → 画师恒为 **2883**。

**2. `rng.randrange(n)` 替代 `seed % n`** —— 熵不再塌缩，顺序种子不再相关。

**3. `rng.sample(tags, k)` 替代 `tags[:8]`** —— 直接消除字母序偏差。实测 `s/t/w/z/m/p` 开头从 **0%** 恢复到接近全量分布。

**4.（可选，改动最大）组合式抽样** —— 不再「抽一整行」，而是「每槽从分类池独立抽」：

```
槽位池（扫 20000 行建成）：
  clothing 3562 | count_identity 3472 | pose_action 2037 | scene 1747
  appearance 1388 | detail_mood 460 | expression 419 | camera 87

组合空间：k=5 时约 2^343  vs  现状 2^12.3
```

三个收益：能生成数据集中不存在的新组合；每槽独立配额可**配平**（现状 clothing+appearance 占 57%，配额后降到 18.5%/22.2%）；可对长尾加权（detail_mood 池里 **48%** 出现次数 ≤2，几乎抽不到）。

#### 但第 4 条有个代价，得说清楚

组合式抽样会拼出**语义不连贯**的结果。实测一次结果里出现几个 `character_name` 标签：

| 方式 | 平均 | 1 个 | 2 个 | ≥3 个 |
|---|---|---|---|---|
| 整行抽取 | 1.48 | **55%** | 22% | 11% |
| 组合式 | 1.98 | 2% | **97%** | 0% |

组合式的 97% 都是 2 个角色，而且来自不同作品：
```
seed=11 -> sela_(23) + fujiwara_chika
seed=12 -> goomba + naga_(nikke)
```

**整行抽取之所以自洽，是因为那些标签在真实图片里确实共现过。** 组合式丢掉了这个约束。

**这正好是 laya 的用武之地，而且完美契合「只判断不排序」**：用 noul 问「这组标签是否只描述单一主体 / 是否存在互斥标签」，不合格就换种子重抽（拒绝采样），而不是让模型在候选里排序。

所以完整的架构是：**组合式抽样负责多样性，laya 质量门负责连贯性** —— 两者配套，缺一不可。但注意前置条件：laya 英文版只有 **512 token** 上下文，而组合式输出 27 个标签约 360 token，必须留足余量；且**零样本准确率只有 0.35 左右**（详见 2b.2），所以质量门要设成「宁可放过、不可卡死」—— 连续 N 次不合格就退回整行抽取模式，绝不能让节点出不来结果。

### 2b.1c 标签抽取算法：第三代（收益在正确性，不在速度）

前两代解决的都是"慢"。第三代解决的是**错**。

#### 三代实测对比（`taglists-sensitive.txt`，全量 100000 行）

| 查询 | A 原始（扫到 5000） | B 拒绝采样（01 号） | C 倒排索引（新） |
|---|---|---|---|
| 无过滤 | 73.0 ms | 0.02 ms ✅ | 0.01 ms |
| 必含 `1girl+solo` | 72.9 ms | 0.02 ms ✅ | 6.22 ms |
| 必含 `blonde_hair+blue_eyes` | 705.9 ms | 0.04 ms ✅ | 2.96 ms |
| **必含 4 项（严格）** | **977.9 ms** | 0.18 ms **✗ 违规** | 6.80 ms |
| 排除 `commentary` | 113.1 ms | 0.02 ms ✅ | 4.95 ms |

#### 问题 1：拒绝采样会静默违反过滤条件

命中率低时，32 次尝试全失败的概率（实测 30000 行样本）：

| 查询 | 命中率 | 32 次全失败率 |
|---|---|---|
| 必含 `1girl` | 86.47% | 0.0% |
| 必含 `1girl+solo` | 74.53% | 0.0% |
| 必含 `blonde_hair+blue_eyes` | 6.88% | 10.2% |
| **必含 4 项** | **0.38%** | **88.4%** |
| 必含 5 项 | 0.36% | 89.2% |

失败后 `pick_taglist` 返回"最后抽到的那行"—— 那行根本不满足条件。**用户设了"必须包含 twintails"，结果里没有 twintails，界面上没有任何提示。**

实测 200 次严格查询：**纯拒绝采样违规 178 次（89%），混合三级 0 次。**

#### 问题 2：原始算法的候选池被截断且有偏

```python
if len(valid_taglists) >= 5000:
    break
```

只从文件开头扫，够 5000 条就停。后果：
- 命中率高时：只从**最前面 5000 条**里抽。实测「必含 1girl」实际有 86557 条匹配，**只用了 5.8%**
- 命中率低时：扫到文件尾也凑不够，耗时 **978 ms**

无论哪种，分布都偏向文件头部。

#### 第三代：混合三级（不是用 C 取代 B）

C 在宽松查询上反而更慢（6 ms vs 0.02 ms），所以正确做法是**快路径优先、逐级升级**：

```
第 1 级  拒绝采样（tries=8）      0.01~0.04 ms   宽松查询首次命中
  ↓ 失败
第 2 级  倒排索引精确交集         0.9~7 ms      保证结果满足条件
  ↓ 索引未就绪（仅预热期）
第 3 级  全量扫描 + 子串预筛      ~1 s          兜底，仍然精确
```

第 2 级做法：must 按 posting 长度升序，从最短的开始做集合交，再减掉 exclude。实测严格查询返回 388 条真实候选，全部满足条件。索引构建 **1.06 s / 4.42M postings / 17.7 MB**（CSR 扁平数组；用 `list[list[int]]` 要 140+ MB），后台线程预热即可。

端到端实测（30000 行样本）：

```
无过滤                    0.03ms  reject       ✓
必含 1girl                0.01ms  reject       ✓
必含 blonde+blue_eyes     0.86ms  index        ✓
必含 4项(严格)             1.03ms  index        ✓
必含不存在tag              0.07ms  index-empty  (无解，明确返回)
排除 commentary           0.04ms  reject       ✓
必含1girl+排除commentary   0.01ms  reject       ✓
```

#### 附带：解析本身 1.90x

现状对每个 token 调一次 `strip().lower().replace()`。改成整行先归一化（2 次 C 层 str 操作），分隔符 `", "` 随之变成 `",_"` 再 split：

```
现状: 7.8 µs/行      优化: 4.1 µs/行      加速 1.90x
全量 100000 行: 782 ms -> 412 ms
```

**已在 20000 行真实数据上逐行比对，输出完全一致（0 处差异）。**

实现见 `patches/07_tag_extract.py`。

### 2b.1d 冲突 tag 处理：面向出图准确性

**结论：能改进，而且现状这个模块基本没在工作。**

#### 现状有多失效

`CONFLICT_PAIRS` 有 23 对硬编码。在 20000 行真实数据上逐对统计命中：

```
from_front + from_behind      0 行      solo + hetero           0 行
from_above + from_below       0 行      solo + yuri             0 行
blindfold + glasses           0 行      missionary + doggystyle 0 行
... 共 14 对 0 命中 ...
pantyhose + barefoot         43 行   ← 最多的一对
sleeping + looking_at_viewer 26 行
open_mouth + clenched_teeth  15 行
```

**只有 9/23 对能命中，最多的也只有 43 行（0.2%）。** 实测 8000 行：现状只影响 **169 行（2.1%）**。

#### 三个 bug

**Bug 1 — 检测和移除用了两套匹配逻辑**

`check_conflicts()` 用 `_find_tag()`（**精确匹配**），`_remove_conflicts()` 用 `if norm_a in tn`（**子串匹配**）：

```
输入: 1girl, solo, pov, lap_pov, full_body
检测: "'pov' conflicts with 'full_body'"        ← 报 1 对
移除: 删掉 pov, lap_pov, full_body               ← 删了 3 个
```

用户看到的警告和实际发生的删除对不上。

**Bug 2 — 子串误伤**：`lap_pov` 被 `pov` 误伤、`solo_focus` 被 `solo` 误伤、`wide_spread_legs` 被 `spread_legs` 误伤（同义强调，不是冲突）。

**Bug 3 — 冲突时两个都删**：
```
looking_at_viewer + facing_away → 两个都删 → 视角信息全丢
```

#### 核心洞察：维度内多值 ≠ 冲突

最直觉的改法是「按视觉属性分组，组内互斥就删」——**这是错的**，会删掉大量合理描述。实测 8000 行：

| 组合 | 共存率 | 性质 |
|---|---|---|
| `1girl + solo` | **74.4%** | 不同维度，必须保留 |
| `breasts + large_breasts` | **57.9%** | 细化，必须保留 |
| `long_hair + very_long_hair` | **24.6%** | 细化，必须保留 |
| `long_hair + ponytail` | 9.8% | 不同维度 |
| `open_mouth + smile` | 9.6% | 不同维度 |
| `2girls + multiple_girls` | 9.2% | 伞形 |

一刀切的话这些全被删，出图质量直接崩。

#### 两个必须做的豁免（漏了就是灾难）

**① 伞形标签**：
```
multicolored_hair  出现 1210 行，其中 99% 同时有 ≥2 个其他发色
two-tone_hair      出现  403 行，其中 100% 同时有 ≥2 个其他发色
heterochromia      出现   95 行，其中  88% 同时有 ≥2 个其他瞳色
```
不豁免，所有多色发型/异色瞳的合理描述会被全部误删。

**② 多人场景** —— 这个最容易漏：

存在 ≥2 种发色（且无伞形标签）的行共 763 行，其中：
- **595 行（78%）含多人标签** → 不同角色不同发色，**完全合理**
- 168 行（22%）是 solo/1girl → 同一角色两种发色，真冲突

```
2girls + black_hair + purple_hair
  两个女孩，一个黑发一个紫发 —— 正常的多角色描述
  不豁免会被删成单一发色，出图直接错
```

#### 最终效果（8000 行真实数据）

| 算法 | 删除 tag 数 | 影响行数 | 平均删/行 | 误伤互补组合 |
|---|---|---|---|---|
| 现状（23 对） | 370 | 169 | **2.19** | **88 次** |
| 新版（分层模型） | 640 | 534 | **1.20** | **0 次** |

覆盖 **3.2 倍**的行，误伤 **归零**，且从「双删丢信息」变成「删一个留一个」。

（诊断说明：最初统计新版还有 68 次"误伤"，追查后发现全部是因为同组里存在第三个标签 —— 62 次同时有 `short_hair`、6 次同时有 `facing_away`，都是真冲突删得对。**真正误伤 0 次**。）

#### 设计

```
L0 豁免     伞形标签（multicolored_hair / heterochromia...）
            多人标签（2girls / 3girls / multiple_girls...）
            → 发色/瞳色维度整体跳过
L1 硬互斥   发色 / 瞳色 / 构图（整组互斥）
            视角 / 发长（成对列举，因为组内混合了互斥与互补）
L2 层级细化 very_long_hair ⊃ long_hair（可选，默认关）
L3 互补白名单 明确不处理
```

**为什么视角、发长必须成对列举而不是整组互斥**：同一维度内混着两种关系。
- 视角：`from_front ↔ from_behind` 是互斥（0 行共存），但 `from_behind + looking_at_viewer` 有 792 行（9.9%）—— 背对镜头但回头看，完全合理
- 发长：`short ↔ long` 互斥（3.2%），但 `long + very_long` 是细化（24.6%）

**删哪个**：保留第一个出现的（CLIP 对靠前 token 权重更高），全程确定性 —— 有冲突时不引入随机，否则种子复现又失效。

**L2 默认关闭**：`long_hair + very_long_hair` 在 SD 里会互相强化，删掉一个可能弱化特征。这是「去重」不是「修冲突」。

实现见 `patches/09_conflicts.py`。

### 2b.2 laya 到底是什么 —— 先纠正一个认知

> **更正**：本方案早先的 `05_laya_judge.py` 把 laya 当普通 HF 模型（取 yes/no logits）处理。
> 查完官方模型卡和基准后，**这个理解要修正**。以下是核实过的结论。

**laya（`convaiinnovations/laya`）不是生成模型，是决策引擎。**

- 421M 参数，**非自回归编码器**（ModernBERT-large），不是 LLM
- 一次前向约 **33ms（T4）**，读一遍 state，同时给所有选项打分
- 三个原语：`choice`（多选一）/ `score`（有序等级）/ `noul`（是/否+概率）
- 所有问题**共享一次前向**：1 问 33ms，10 问 72ms，50 问 337ms
- 上下文：英文版 **512 token**，多语言版 1024（typed-decisions 1024）
- Apache 2.0，`pip install laya`

**它取代不了 LM Studio** —— 你现在用 LM Studio 干的是「把标签扩写成自然语言」，那是**生成**，laya 一个字都生成不了。两者并列，不是替换：
```
决定「这批标签要不要」  -> laya      （33ms，本地）
把标签写成自然语言      -> LM Studio （秒级）
```

#### 四个会直接绊倒你的限制（都是官方模型卡自己写的）

| # | 限制 | 数据 | 后果 |
|---|---|---|---|
| 1 | **零样本接近随机** | 基础版 typed-decisions **0.362**，随机猜 0.318，多数类 0.461 | 那个 0.766 是**微调后**的。模型卡原话："Laya is a fast base to specialise, **not a zero-shot decision engine**." |
| 2 | **choice 超过 20 个选项就崩** | Banking77（77 选项）只有 0.425 | 选项共享 192 token 预算，77 个选项每个只剩 3~4 token |
| 3 | **概率默认过度自信** | 原始 ECE **0.466**，重拟合温度后降到 0.081 | 必须按「题型 × 选项数」各自重拟合才能用阈值过滤 |
| 4 | **`action.act_probability` 是坏的** | AUROC 0.30（对比 `confidence` 0.77） | 门控必须用 `confidence`，不能用 act_probability |

#### 按原语看强弱：**noul 最强**

| 原语 | 准确率 |
|---|---|
| **noul**（是/否） | **0.857** |
| choice | 0.733 |
| score | 0.723 |

所以：**问窄二值命题，别问开放判断题。**

```
✗ "这组标签质量好不好？"        —— 开放判断，零样本接近随机
✓ "这组标签里是否包含元数据标签？"  —— 窄二值，noul 的强项
✓ "这两个标签是否互斥？"
✓ "这条记录是否只描述单一主体？"
```

#### 正确的集成方式：质量门 + 拒绝采样

不是「从 N 个候选里挑最好的」（那违反限制 2，而且零样本下 argmax 也没意义），而是官方推荐的 **Cascade**：

```
抽签 -> laya 判断（一次 predict，几个 noul 问）-> 合格? -> 输出
         ^                                          |
         |____________ 不合格，换个种子重抽 ___________|
```

一次 predict 33~72ms，重抽 3 次也才 200ms —— 相比 LM Studio 的秒级 NL 生成完全可以忽略。

#### 和前面随机内核的关系

这印证了 2b.1b 的结论，而且把顺序定死了：

1. **先验条件是标签数上限**：现在每行中位数 45 个、最大 746 个。746 个标签 ≈ 4000+ token，**英文版 512 上下文根本塞不下**。必须先 cap（建议 60 个 ≈ 360 token），再留 4 个问题（≈120 token）才进得去。想宽松就用多语言版（1024）。
2. **加载必须后台**：加载耗时 25~35 秒，绝不能放在 `INPUT_TYPES` 或首次执行时同步跑（和 `03_lm_studio_fix.py` 里 `lms` 的问题一模一样）。
3. **拒绝采样和组合式抽样是配套的**：组合式抽样（2b.1b 第 4 条）会拼出跨作品角色冲突，正好用 noul 问「是否只描述单一主体」来卡 —— 不合格就换种子重抽。这符合「只判断不排序」。

#### 现实预期与落地顺序

**先纠正我前面的判断：微调不是可选增强，是集成的前置步骤。**

零样本基础版在 typed-decisions 上是 **0.362**，而随机猜 0.318、多数类 0.461。这意味着零样本门**不只是没用，是负收益** —— 白加 33ms 延迟，还随机拒掉好结果、随机放过坏结果。模型卡说得很直白："Laya is a fast base to specialise, not a zero-shot decision engine."

正确顺序：

```
确定性修复 → 生成训练数据 → 微调 → 温度校准 → 集成
```

**"先微调"不等于"其他都不用做"** —— 确定性修复是微调的前置条件：训练数据里现在有 5.3% 是元数据垃圾标签，直接拿去训练，laya 会学到「`commentary` 是正常标签」；`[:8]` 的字母序偏差同理，模型会把「a/b/c 开头更常见」当成真实分布。

#### 自动标注不用人工，但有个会毁掉整个微调的陷阱

你有 10 万行真实 Danbooru 标签行，天然就是正例（真实共现）。负例可以合成 —— **但最直觉的那种负例是错的**：

**【陷阱】N1 跨行混拼**（把两行各取一半拼起来）

实测：**随机拼出的角色对，在真实数据里出现过的比例 = 0.00%**

正负例可以被「这个组合我见没见过」**完美分开**，模型不需要理解任何语义，记住共现表就能拿满分。

后果是灾难性的：部署时组合式抽样产出的全是**新组合**，一个只会记忆的模型会把它们 100% 判为「不连贯」→ 全部重抽 → **退化成整行抽取，组合式带来的多样性全部作废**，还白搭 33ms 延迟。

**【正确做法】N2 温和扰动**：把 1 个 tag 换成**同槽位 + 同频率带**的另一个 tag。

| 负例类型 | 仅用「平均 tag 频率」判别 AUC |
|---|---|
| N1 跨行混拼 | 0.540 |
| **N2 换 1 个同槽同频 tag** | **0.522**（平凡特征几乎无效） |

N2 的负例在频率、槽位结构上和正例完全一致，唯一区别就是**语义上搭不搭** —— 模型只能真的去学语义。

```
原: 1girl, bikini, blue_eyes, blue_hair, blush, breasts, butt_crack
换: 1girl, bikini, blue_eyes, blue_hair, blush, wide_hips, butt_crack
                                              ^^^^^^^^^ 同槽同频，但不搭
```

实测生成的数据（2000 对，已过滤垃圾标签）：
```
训练 3200 条 / 验证 800 条，正负各半
残留垃圾标签样本: 0 条 ✓
平凡特征可分性: 平均频率 AUC 0.520 ✓ | 标签数 AUC 0.473 ✓
```

#### 验证集必须包含「新组合」

训练和验证都从「真实 vs 合成」切分的话，验证集是同分布，**看不出模型是不是在记忆**：

- **验证A**：held-out 的 N2 对（同分布，看拟合）
- **验证B**：从未参与训练的真实行 + 组合式抽样的真实产出 ← **这才是部署时的输入分布**

**A 上 0.9 但 B 上 0.5 = 在记忆，白训了**，回去改负例构造。

#### 数据量没那么吓人

官方 `laya-typed-decisions` 只用了 **1200 case / 6000 decision** 就训到 0.766。所以几千条高质量 N2 对就有机会 —— **优先保证负例质量而非数量**，建议 5000~10000 对起步。官方有免费 Kaggle 2×T4 notebook，约 4~5 小时。

实现见 `patches/07_laya_finetune.py`（负例构造 + 数据集生成 + laya 格式转换 + 上线检查清单），集成见 `patches/06_laya_gate.py`。

### 2b.3 成本控制（这是 laya 能不能落地的关键）

0.4B 单次前向是**内存带宽受限**（fp32 权重 1.6GB，CPU 读一遍约 16ms），所以：

**1. 必须 batch。** `batch=8` 的耗时接近 `batch=1`，千万别写 for 循环逐个推理。

**2. 批量模式要先去重 —— 这是让它可行的关键**（实测）：

| 种子数 | 朴素（逐种子判） | 全局去重后判一次 | 压缩比 |
|---|---|---|---|
| 16 | 926 | 531 | 1.7× |
| 64 | 3303 | 1209 | 2.7× |
| 256 | 12987 | **2598** | **5.0×** |

256 个种子最终只需判断约 2600 个唯一 tag，按 batch=32、单次前向 30ms 估算 **≈ 2.4 秒**，可接受。做法：先对所有种子的 tag 去重 → 批量判一次 → 之后全部走字典查表。

**3. 冲突判断要先粗筛**（实测单个候选 53 个 tag）：

| 方式 | 对数 |
|---|---|
| 全两两 O(n²) | 1378 对 |
| 仅**同槽位内**两两 | **177 对（13%）** |

降了一个数量级。别把 1378 对全塞给模型。

**4. 降级必须完整**：模型没装 / 加载失败时，`judge_keep` 退回 `[:8]`、`judge_prefer` 退回「留 A」、`judge_candidates` 退回「取第 0 个」—— 都比现状好或持平，节点照常工作。已实测三条降级路径均不抛异常。

**5. 建议的节点开关**：
```
▸ laya 判定
  laya模型路径    STRING  默认 models/laya-0.4b
  启用tag筛选    BOOLEAN 默认 True   （judge_keep）
  启用冲突判定   BOOLEAN 默认 False  （需先修双删）
  候选数N        INT     默认 1，单次模式可调到 8
  保留阈值       FLOAT   默认 0.5
```

### 2b.4 接入方式

补丁 `patches/05_laya_judge.py` 里 `MERGE_SLOTS_PATCH` / `CONFLICT_PATCH` / `RAFFLE_PATCH` 三个常量是逐行的 diff，可直接照着改。

优先级：**先做 2b.1 的 5 处纯规则修复**（零依赖、零风险、立刻见效），再上 laya 的 A（judge_keep），B 和 C 视效果再开。

      if ensure_model_loaded(...):

（pyflakes 也报了：`anima_weaver.py:453: undefined name 'auto_ctx'`）

那一段用的是 `kwargs_raw`，但 341 行写成了 `kwargs.get(...)`，同样被 `try/except` 吞掉。
